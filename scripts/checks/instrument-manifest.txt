# instrument-manifest.txt — THE WAIVER LEDGER of universal gate item 9
# (`scripts/checks/check-instrument-typecheck.sh`, `03-quality.md` §3.1).
#
# ---------------------------------------------------------------------------
# WHAT THIS FILE IS. It listed what IS compiled. It now lists what is NOT — and
# the target is that it lists NOTHING.
#
# The gate enumerates its subjects by GLOB over the whole of `scripts/checks/`,
# at any depth, dotfiles included, `.ts` and `.tsx` (`.mts`/`.cts` are named and
# failed by its coverage scan). Coverage is automatic and cannot be forgotten.
# What this file holds is the other thing: an instrument that genuinely cannot
# be made to compile by the project standing in front of it, EXCUSED IN THE
# OPEN, with a diagnostic, a reason and an owner attached to it.
#
# ADDING A PATH HERE DOES NOT OBTAIN COVERAGE — IT EXCUSES A FAILURE. There is
# no way to "get a file compiled" by writing it down. Every file under
# `scripts/checks/` is compiled the moment it exists, including one written by
# someone who never read this file or the plan behind it. A line here changes
# one thing only: an observed FAIL is reclassified as an excused WAIVED, and it
# is printed, loudly, in every transcript until someone removes it.
#
# THE LEDGER IS EMPTY AT THE TIME OF WRITING, AND THAT IS THE TARGET STATE, NOT
# AN OVERSIGHT. All 42 subjects compile clean (round 500, `evidence/
# phase5-ledger.md`; the six that were red were fixed at the source in phase 3,
# not excused here). An empty ledger is what this project set out to leave
# behind. The file is kept rather than deleted because DELETING IT WOULD MAKE
# THE NEXT EXCLUSION INVISIBLE: with no ledger, the next person facing one
# stubborn instrument reaches for an `--exclude` flag or an `if` in the compile
# loop — a quiet, unowned, unprinted exclusion, which is exactly the shape this
# project exists to eliminate.
#
# ---------------------------------------------------------------------------
# THE FORMAT — FOUR REQUIRED FIELDS PER ENTRY (`02-architecture.md` §4.6).
#
# The example below is INDENTED BY FOUR EXTRA SPACES so that the gate does not
# read it as a live record. A field line is recognised as `# ` followed
# IMMEDIATELY by the field name — which is exactly what a real entry looks like,
# and exactly what an example in a header must not be.
#
#     path        : scripts/checks/check-example.ts
#     diagnostic  : TS2345 at line 88 — <verbatim first line of the error>
#     reason      : <why it cannot be fixed by the project holding it>
#     owner       : <the project or round that will fix it>
#     scripts/checks/check-example.ts
#
# A real entry is those same five lines with the four field lines beginning at
# column 1 as `# path        : …` and the fifth being the bare path, neither
# indented nor commented. All four fields are REQUIRED and none may be empty:
# the gate fails, naming the path and the missing field(s). A field block with
# no bare path after it fails the same way — a justification that excuses
# nothing is a note, and notes belong in prose, not in a ledger.
#
# ---------------------------------------------------------------------------
# THE THREE PROPERTIES THAT MAKE A LEDGER SAFER THAN AN EXCLUSION FLAG. All are
# implemented in the gate — step 8 reads this file, step 11 reconciles it —
# and each landed in the same commit as the header text claiming it (standing
# rule 2): the first two at round 500, the third at round 501.
#
#   1. EVERY WAIVER IS PRINTED ON EVERY RUN, in the WAIVERS block above the
#      verdict, with its four fields and with the diagnostic the compiler
#      ACTUALLY produced beside the one recorded here. A waiver cannot be
#      quiet. With zero entries the block still prints — "ok: 0 waivers — the
#      ledger is empty" — because a block that vanishes when it is empty is a
#      block nobody notices has stopped running.
#   2. A WAIVED FILE THAT COMPILES CLEAN IS A FAILURE — the gate says "waived
#      but clean" and names it. Stale waivers are the mechanism by which an
#      exclusion list outlives its reason: the error gets fixed, the excuse
#      does not get deleted, and the next reader believes the file is still
#      broken. Two further failures close the same hole from the other side: a
#      waived path that is not on disk, and a waived path the gate does not
#      compile at all, are both refused — a waiver must name something this
#      gate actually reads, or it is excusing nothing and hiding that fact.
#   3. ONE SUBJECT, ONE WAIVER — A PATH WRITTEN HERE TWICE IS A LEDGER ERROR,
#      and the gate names BOTH line numbers. This one was missing until round
#      501 and its absence was the hole properties 1 and 2 were supposed to
#      make impossible: step 11 discounts ONE observed failure per valid entry,
#      so a second entry for the same path discounts a failure IT DOES NOT OWN.
#      Measured — two broken subjects, one of them waived twice with two
#      perfectly valid four-field entries: the gate printed both failures, then
#      `type failures 0`, then `PASSED`, and exited 0 over an unexcused TS2322
#      in a file nobody had waived (`evidence/phase6-ledger-c4.md`, control C4).
#      A duplicated path is an ordinary hand-edit slip — two projects excusing
#      the same stubborn instrument, or one copy-paste — which is exactly why
#      it is refused rather than quietly ignored: a skip would repair the
#      arithmetic while leaving you believing this file says what you wrote. If
#      two rounds need to waive one path, they share ONE entry and its
#      `diagnostic` field names both errors.
#
# THE LEDGER NEVER EXCLUDES A FILE FROM COMPILATION. Every subject is compiled,
# every run, waived or not; the waiver acts on the VERDICT, never on the
# subject list. There is no `--exclude` path in the gate and this file must not
# grow one.
#
# ---------------------------------------------------------------------------
# THE LAUNCH GOAL'S PHRASING WAS SUPERSEDED, AND `scripts/deploy/payload-
# verify.json` STILL QUOTES IT VERBATIM — correctly, because it is the record
# of what was launched. The goal reads: "extend scripts/checks/instrument-
# manifest.txt to cover the whole directory". That sentence was written when
# this file was an inclusion list, and it describes a way of obtaining coverage
# that no longer exists. THE DIRECTORY IS COVERED WITHOUT THIS FILE NAMING
# ANYTHING: glob enumeration in the gate (R8, R9) covers it, and the goal's
# intent — every script under `scripts/checks/` under a typecheck gate — is met
# with this ledger empty. `payload-verify.json` is not edited: editing a record
# of what was launched falsifies it.
#

# HISTORY (round 800) — WHAT THIS FILE USED TO BE. It was an INCLUSION LIST:
# the gate compiled the paths named here and nothing else, and a "manifest
# guard" (`git diff --diff-filter=ACMR main..HEAD -- 'scripts/checks/*.ts'`)

# author remember to list their file" is a question that exists only because
# there is a list — and with a glob there is nothing to forget.
#
# HISTORY (round 800) — THE RATIONALE THAT WAS RETIRED, verbatim in substance:
#
#   WHY A MANIFEST AND NOT THE WHOLE DIRECTORY. MEASURED AT ROUND 800.
#   6B's invocation over all 25 `scripts/checks/*.ts` in ONE invocation does not
#   pass and CANNOT be made to pass by this project:
#     * compiled together they pull `forge-control-web/app` into the program,
#       and `useAutogrow.ts` and `tokens.ts` then fail on DOM lib resolution;
#     * three other projects' scripts are independently red —
#       `check-orientation.ts` (3 type errors plus a `--jsx` failure),
#       `serve-sse-808.ts` (implicit `any`s), `check-chat-rich.tsx`.
#   A gate that can only ever be disclosed is the failure standing rule 2 exists
#   to kill. So the gate is scoped to what this branch OWNS and can fix, and it
#   GROWS BY CONSTRUCTION: check-instrument-typecheck.sh fails, by name, if any
#   `scripts/checks/*.ts` this branch added or modified is missing from this
#   file.
#   MEASURED AT ROUND 800: one file per invocation, all six below exit 0 with
#   zero errors — check-close-gate.ts, check-fix-chain-graph.ts,
#   check-plan-api.ts, check-plan-store.ts, check-project-metadata.ts,
#   check-task-api.ts.

# WHAT SUPERSEDED IT: the profile `tsconfig.checks-instruments.json` (phase 1)
# made the merged-program argument moot — every subject is compiled ALONE
# (R11), through one `extends` of the app's own tsconfig — and phase 3 fixed
# the three red scripts at the source rather than excusing them. Measured at
# round 500: 42 subjects found, 42 compiled, 0 failures, one tsc invocation per
# file, glob-enumerated. The seven paths this file used to name were deleted in
