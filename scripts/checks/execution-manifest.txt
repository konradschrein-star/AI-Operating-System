# execution-manifest.txt — THE OPEN LEDGER of the EXECUTION REGISTRY
# (`scripts/checks/check-instrument-execution.ts`, wired into `guard.sh` phase 1).
#
# ---------------------------------------------------------------------------
# WHAT THIS FILE IS. It is the twin of `instrument-manifest.txt` one axis over.
# That file is the waiver ledger of the COMPILE registry, which globs every
# `.ts`/`.tsx` under `scripts/checks/` and type-checks it. This one is the
# ledger of the EXECUTION registry, which globs every `.ts/.tsx/.sh/.cjs/.mjs/
# .py` under `scripts/checks/` plus every tracked `*.test.ts(x)` in the repo,
# and asks the question nothing in this repo asked until 2026-08-25: does
# ANYTHING RUN IT?
#
# The answer that day was no, 41 times, and one of the 41 was
# `check-secret-scan.ts`, sitting over a real committed credential while the
# suite reported `RED: 0` (`docs/plan/artifacts/verification-that-bites/
# D1-execution-audit.md`). Compiling is not running. A green tick for
# compiling, printed next to a gate name in a list, is what made that
# invisible for four months.
#
# ADDING A PATH HERE DOES NOT OBTAIN COVERAGE — IT EXCUSES A FAILURE. There is
# no way to "get a file executed" by writing it down. Every artefact under
# `scripts/checks/`, and every tracked test file, is a subject of the check the
# moment it exists, including one written by someone who never read this file.
# A line here changes exactly one thing: an observed "executed by nothing" is
# reclassified as an excused exclusion, and it is printed, in full, with its
# four fields, in EVERY transcript until someone removes it.
#
# A LIVE-ORPHAN MAY NOT BE LEDGERED, AND THIS FILE CANNOT EXPRESS ONE. The
# `bucket` field takes three values and only three:
#
#   SPENT             a one-shot verification of a round that has settled. Its
#                     subject question was answered; nothing is protected by
#                     running it again.
#   NOT-A-CHECK       a harness, a server, a fixture, a tool. It has no verdict
#                     of its own to lose.
#   PROCEDURE-INVOKED a CURRENT doc still instructs a human to run it, going
#                     forward — cited by file:line. Materially weaker than a
#                     wired gate (a runner fires unconditionally; a doc fires
#                     only if someone reads it) and materially stronger than
#                     nothing. A historical evidence report narrating a run
#                     that already happened DOES NOT COUNT.
#
# Anything else — including the words LIVE-ORPHAN — is a LEDGER ERROR that
# fails the run by name. A live gate that nothing executes is not excusable in
# a file: it is an OPEN FINDING, it lives in `KNOWN_OPEN_FINDINGS` in
# `check-instrument-execution.ts` where it is printed as debt on every run, and
# getting it off that list is a conversation with Konrad, not an edit here.
# `check-secret-scan.ts` is the worked example: it is an open finding, it is
# deliberately NOT in this file, and it will not be wired in until the order
# redact -> rotate -> remove the literal -> wire in has been walked.
#
# ---------------------------------------------------------------------------
# THE FORMAT — FOUR REQUIRED FIELDS PER ENTRY.
#
# The example below is INDENTED BY FOUR EXTRA SPACES so that the check does not
# read it as a live record. A field line is recognised as `# ` followed
# IMMEDIATELY by the field name — which is exactly what a real entry looks
# like, and exactly what an example in a header must not be. This is not
# hypothetical: `instrument-manifest.txt` had to solve the same problem and
# the AI OS memory note `header-example-is-live-syntax` records the run where
# a gate read its own documentation as a waiver.
#
#     path    : scripts/checks/check-example.ts
#     bucket  : SPENT
#     reason  : <why nothing needs to run it — a fact, not a preference>
#     owner   : <the person, project or round answerable for that claim>
#     scripts/checks/check-example.ts
#
# A real entry is those same five lines with the four field lines beginning at
# column 1 as `# path    : …` and the fifth being the bare path, neither
# indented nor commented. All four fields are REQUIRED and none may be empty:
# the check fails, naming the path AND the missing field(s). A field block with
# no bare path after it fails the same way — a justification that excuses
# nothing is a note, and notes belong in prose, not in a ledger.
#
# ---------------------------------------------------------------------------
# THE PROPERTIES THAT MAKE A LEDGER SAFER THAN AN `--exclude` FLAG. All are
# implemented in the check, and each landed in the same commit as this text.
#
#   1. EVERY ENTRY IS PRINTED ON EVERY RUN, in the LEDGER block above the
#      verdict, with all four fields. An exclusion nobody sees is an
#      `--exclude` flag with extra steps. With zero entries the block still
#      prints — "ok: 0 entries — the ledger is empty" — because a block that
#      vanishes when it is empty is a block nobody notices has stopped running.
#   2. A LEDGERED PATH THAT IS ACTUALLY INVOKED IS A FAILURE. The check says
#      "ledgered but INVOKED" and names the runner and line. This is how an
#      exclusion list outlives its reason: someone wires the check in, nobody
#      deletes the excuse, and the next reader believes the artefact is dead.
#   3. A LEDGERED PATH THAT IS NOT ON DISK, OR THAT IS NOT A SUBJECT OF THIS
#      CHECK, IS A FAILURE. An entry must name something the registry actually
#      reads, or it is excusing nothing and hiding that it does.
#   4. ONE SUBJECT, ONE ENTRY. A path written here twice is a ledger error and
#      the check names both line numbers.
#   5. THE LEDGER NEVER REMOVES A FILE FROM THE SUBJECT SET. Every subject is
#      resolved against the runners on every run, ledgered or not; the entry
#      acts on the VERDICT, never on the subject list. There is no `--exclude`
#      path in the check and this file must not grow one.
#
# ---------------------------------------------------------------------------
