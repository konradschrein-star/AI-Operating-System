NOTE 1 — THE CONNECTION STRING IN THE BRIEF DOES NOT AUTHENTICATE.

  psql "postgresql://postgres:content_forge_prod@127.0.0.1:5432/content_forge"

        FATAL:  password authentication failed for user "postgres"

`content_forge_prod` is the *fallback literal* in forge-control/src/db/reminders.ts:17,
reached only when DATABASE_URL is unset. It is not the password this box runs. The live
forge-control, forge-executor and forge-control-web processes are all started with a
DATABASE_URL pointing at the SAME host, port and database (127.0.0.1:5432/content_forge)
with a different 30-character password, and that is the connection used above.

This is the good failure mode: a wrong password ERRORS. The fleet's standing hazard is the
other one — a wrong *instance* answers 0 rows and reads as a finding. The total asserted
here is 177, three digits and in the expected band, so the connection is sound.

NOTE 2 — S12 ("identical before and after") IS NOT SATISFIABLE AS WRITTEN. READ THIS
BEFORE FAILING PHASE 6 ON IT.

The table is written to continuously by this fleet's own agents. Two counts taken five
minutes apart during THIS task:

  2026-08-18T20:16:06Z  ->  176
  2026-08-18T20:21:03Z  ->  177
  2026-08-18T20:21:40Z  ->  179     (three rows in 5m34s, none of them written by this task)

63 rows were created on 2026-08-18 alone, against 5 on 2026-08-16. The producers are
worker escalations from the very project that phase 6 belongs to, plus watchdog
auto-unwedge notices. The count will therefore differ before and after phase 6 no matter
what phase 6 does, and a literal reading of S12 fails the phase for other agents' traffic.

What S12 actually needs to assert, and what a verifier should use instead:

  (a) NO ROW IS DESTROYED. Pin the identities, not the count:
        SELECT count(*) FROM reminders WHERE id IN (<the 177 ids at this timestamp>);
      -- must still be 177. Equivalently, the min(created_at) must not move and no id
      -- present now may be absent later.
  (b) NO STATUS IS REWRITTEN BY US. The 20 'dismissed' rows stay 20 or grow (Konrad may
      dismiss); no row may travel delivered -> pending or delivered -> dismissed without a
      user action.
  (c) DELIVERY STILL FIRES. max(created_at) and max(delivered_at) both keep advancing.

Task B wrote NOTHING to this table: no INSERT, no UPDATE, no DELETE. Every statement it
ran was a SELECT.
