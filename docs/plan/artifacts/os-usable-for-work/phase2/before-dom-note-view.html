# 2026-08-19

## Notes

### A lane sat frozen for hours and every instrument said "clear"

The `vault` workstream of `os-usable-for-work` held **seven pending tasks and ran nothing**. The project was `active`. My stalled-project detector, built the day before and controlled in both directions, reported **clear**. It was not lying — it was PROJECT-scoped, and the project genuinely looked busy because the `connections` lane was running. *A per-project health check cannot see a per-lane stall, and the whole point of workstreams is that lanes are independent.*

**The cause was mine.** `promoteReadyTasks()` has a straddle term: a graph row is held back if ANY row with `depends_on IS NULL` sits at a lower round and is not done — **project-wide, across unrelated workstreams**. When I compressed three integration tasks into one and their three reviews into one, I inserted the two replacement rows **by hand, without `depends_on`**. Born legacy-null, they became barriers. The compression that saved eight sessions silently serialised four lanes behind a row that had nothing to do with three of them.

That is the **second** time a hand-seeded row wedged this project. The first was retiring tasks as `blocked`. Different column, identical shape: *the engine's rows are always well-formed; mine are the ones that are not.*

Fixed by giving all four rows real dependencies — the merged integrator now names the terminal task of each lane it merges (both connections re-reviews, since that lane also carries two live fix chains), and its review names the integrator. Verified R14 cardinality on every touched row (declared == resolved, 4/4), legacy-null non-done rows on the project now **0**. The vault lane picked up `Fix cycle 2 · vault` within the minute.

While in there I **serialised the vault lane deliberately**: one worktree means one session. The fix-cycle-1 re-review now also waits on fix cycle 2, so it reviews a settled tree once instead of a moving one twice, and phase 2's first build waits for the phase-1 verdict. Cheaper and safer than three concurrent sessions fighting over one checkout.

### The detector now tests the thing itself, not a mechanism

New section: **a row that is pending, whose every named dependency exists and is done, and which has not moved in 20 minutes, is wedged** — regardless of cause. Under a correct scheduler that set is empty by construction, so it catches the next mechanism as well as this one. A second section names the specific cause (a legacy row with open graph rows above it) so the next instance is found in seconds.

Controlled **by filter inversion, not by a live wedge** — the wedge was repaired before the check existed, and the script says so in its own comments. Dropping the deps-done term fires 5 rows; inverting it fires 11 disjoint rows; as written, 0. That proves both terms are live. It does **not** prove the check catches a real stall end-to-end, and pretending otherwise would make it exactly the kind of self-certifying instrument I keep finding in other people's work.

### Elsewhere

- **The append race is in flight.** `appendToDailyNote` acknowledged `ok:true` ten times out of ten while writing one line — nine captures gone, no snapshots. The engine had already routed the reviewer's exact three-line fix into the next fix cycle without my help; I went to hand-route it and found the job done. *Check whether the engine already did it before doing it by hand.*
- `engine-task-graph` is on fix cycle 2 (round 964) after its re-review found more. Rounds 970/971 sit above it and wait correctly.
- Phase 7's planner woke up and I gave it the three preconditions it would otherwise have planned straight past — chiefly that **the live checkout is not clean** and a deploy that resets it destroys unclaimed work.
