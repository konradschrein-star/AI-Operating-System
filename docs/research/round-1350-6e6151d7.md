# Connecting Gemini without an API key — the actual routes (R1350)

**Run:** `cb270ce22cab` · **Date of research:** 2026-08-17 · **Researcher lane, no implementation.**

**The question:** what are the real routes from "Konrad holds a Google AI Ultra 20x subscription and a live
Google OAuth refresh token" to "the AI OS can call a Gemini model", and what does each cost in setup,
fragility and ToS risk?

---

## 0. Answer first

**The 2026-08-05 conclusion was right about the raw API and wrong about the world.** Ultra still grants no
Gemini API access — I re-verified that against a primary doc dated 2026-08-04 *and* proved it empirically
against Konrad's own token. But a genuine zero-key route now exists that did not exist in the earlier
research's frame: **Google moved Pro/Ultra entitlements off Gemini CLI onto the Antigravity CLI (`agy`) on
2026-06-18**, and `agy` has a documented headless mode. That is the route.

**Recommendation: install Antigravity CLI, have Konrad complete its SSH paste-a-code login once, and shell
out to the `agy` binary.** Not the SDK, not a lifted OAuth token, not the cookie pool. Reasons and the
disqualifying evidence for each alternative are in §5–§6.

One hard constraint that shapes the whole build (§6.1): we must invoke the **first-party binary**, never
extract its token and call Google ourselves. That is explicitly a ToS violation.

## 1. What I verified locally (empirical, this host, this run)

These are not citations to documents — they are measurements taken on 65.108.6.149 during this run.

### 1.1 Konrad's OAuth token cannot reach Gemini. Proven, not assumed.

`/root/.hermes/google_token.json` refreshes successfully. `oauth2.googleapis.com/tokeninfo` returns the
granted scope list:

```
calendar, contacts.readonly, documents, drive,
gmail.modify, gmail.readonly, gmail.send, spreadsheets
```

No `generative-language.*`, no `cloud-platform`. Calling Gemini with that access token:

```
GET  https://generativelanguage.googleapis.com/v1beta/models                      → HTTP 403
POST https://generativelanguage.googleapis.com/v1beta/models/
       gemini-2.0-flash:generateContent                                           → HTTP 403
```

Both return the same body:

```json
{"error":{"code":403,"message":"Request had insufficient authentication scopes.",
 "status":"PERMISSION_DENIED","details":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo",
 "reason":"ACCESS_TOKEN_SCOPE_INSUFFICIENT"}]}}
```

**Read this error carefully — it is a trap.** `ACCESS_TOKEN_SCOPE_INSUFFICIENT` *looks* like "just re-consent
with a wider scope and it will work". It will not, and §2 explains why: the scope is not the binding
constraint, the billing relationship is. Re-consenting `generative-language.retriever` on a consumer account
with no Cloud project and no billing gets you a different error, not a working model call. **Inference,
flagged as such** — I could not execute the re-consent (that requires Konrad's interactive approval, which
the brief forbids me to seek), so the failure mode of the *widened* scope is reasoned from §2's billing
docs, not observed.

### 1.3 The installer is real and inspectable

`curl -fsSL https://antigravity.google/cli/install.sh` → HTTP 200, 7354 bytes. I downloaded and read it; I

### 1.4 The existing Gemini Pool: live, and riding an account nobody can name

`gemini-api.service` ("Gemini Pool API") and `gemini-socks.service` ("Gemini SOCKS5 egress (residential
proxy)") are both `active running`. `GET http://127.0.0.1:8090/health`:

```json
{"status":"ok","sessions_total":4,"sessions_ready":4,"queue_active":0,"queue_waiting":0,
 "uptime_s":1640962,"avg_response_s":46.18,"egress":"direct (eduVPN kernel routing)"}
```

19 days uptime, 4/4 sessions healthy. It is a Docker Compose app in `/opt/gemini-pool-api`, FastAPI, whose
`requirements.txt` pins **`gemini_webapi>=2.0.0`** — the reverse-engineered library. `cookie_bridge.py`
harvests `__Secure-1PSID` / `__Secure-1PSIDTS` cookies over CDP from Chrome instances on ports 9400–9414
and writes `fresh_accounts.json`.

Two things a planner should know that the vault note does not say:

- `fresh_accounts.json` currently holds **one** account, and its `email` field is **`cdp-9400`** — the
  port-number fallback in `cookie_bridge.py`, used when the `/fx/api/auth/session` email probe returns

  operational blind spot for anything ToS-exposed.
- It is **not** Konrad's Ultra account by design — the vault note says *"Uses a pool of Google accounts
  instead of a personal API key — usage rides on pool account entitlements"*. So the pool does not answer
  the question in the brief; it answers a different one.

Auth is `x-api-key` against `/opt/gemini-pool-api/.env`'s `GEMINI_API_KEY` (a pool-local token, **not** a
Google key — `scripts/gemini-qa.mjs` documents this exact name collision at length).

## 2. Route 1 — Vertex AI / Google Cloud

**Does Ultra grant anything here? No. It is strictly separate consumer billing.** This is the most commonly
confused point and the answer is unambiguous.

> "Google AI plan benefits for developer usage apply only within the Google AI Studio web interface. Direct
> use of the Gemini API (such as using API keys or external applications) is billed and managed separately."
>
> — *Google AI Plans | Gemini API*, https://ai.google.dev/gemini-api/docs/google-ai-plans,
> **page shows Last Updated 2026-08-04**, accessed 2026-08-17

That page also confirms what the subscription *does* buy a developer:

> "Google AI Pro and Ultra subscriptions enable developers to unlock paid models and higher rate limits in
> the Google AI Studio Playground."

Playground — the web interface. Not the API.

**Setup cost:** GCP project + billing account + enable Vertex AI + service account or ADC. Vertex is a
genuine, robust, ToS-clean route — it is simply **not zero-auth and not free**, and Ultra contributes
nothing to it. Gemini CLI's own docs list the Vertex path as requiring `GOOGLE_CLOUD_PROJECT` +
`GOOGLE_CLOUD_LOCATION` plus one of ADC (`gcloud auth application-default login`), a service-account JSON via
`GOOGLE_APPLICATION_CREDENTIALS`, or `GOOGLE_API_KEY`
(https://google-gemini.github.io/gemini-cli/docs/get-started/authentication.html, accessed 2026-08-17).

**Verdict: correct but off-brief.** Recommend only if Konrad later wants billed, SLA-backed, high-volume
Gemini. The brief forbids me to create a project or enable billing, and I did not.

## 3. Route 2 — AI Studio API key (one paste)

Not zero-auth, but the brief asks the right question: is issuance reachable from the account we already
hold, and does a one-paste flow beat a fragile zero-auth flow?

**Issuance is interactive and gated.** I drove a real browser to `https://aistudio.google.com/apikey` in the
`scratch` profile. It redirects to a Google sign-in wall — `research-browser` classified it LOGIN REQUIRED
and I stopped there without attempting credentials, per the lane rules.

![AI Studio API key page — Google sign-in wall](/api/uploads/cb270ce22cab/20260817T042028Z-aistudio-apikey-page.png)
*`/api/uploads/cb270ce22cab/20260817T042028Z-aistudio-apikey-page.png` — browser session, 2026-08-17.*

So: the panel **can** deep-link him to the exact page (`https://aistudio.google.com/apikey`), and he pastes
once. The key then works with `scripts/gemini-qa.mjs --backend api` and every Gemini SDK, immediately.

**The catch is what the key costs to *use*.** A key issued on a project without billing sits on the free
tier, which the Gemini CLI quota page rates at *"250 maximum model requests / user / day"* and *"Model
requests to Flash model only"* (https://geminicli.com/docs/resources/quota-and-pricing/, **Last updated
Jun 18, 2026**, accessed 2026-08-17). Beyond that, the §2 quote applies — billed separately, Ultra
contributes nothing.

**Verdict: the correct fallback, and genuinely competitive.** One paste, zero fragility, zero ToS risk,
works forever. It loses to Antigravity only because it does not use the Ultra subscription Konrad already
pays for and caps at Flash-only 250/day unless he enables billing. **The panel should offer both** (§8).

## 4. Route 3 — `gemini_webapi` / cookie session reuse (the vault's prior art)

**Does it still work in 2026-08? Yes — demonstrably, it is running in production on this box right now**
(§1.4): 4/4 sessions, 19 days uptime. The vault's "real simplicity finding" is real.

**What breaks it:** cookie expiry. `cookie_bridge.py`'s own docstring: *"Harvest FRESH Gemini cookies
(`__Secure-1PSID` / `__Secure-1PSIDTS`) from the live Chrome CDP sessions running on this host"*, and it
must re-navigate to `gemini.google.com` each run *"so cookies are always fresh"*. The upstream library
*"automatically refreshes the `__Secure-1PSIDTS` cookie in the background while the process is alive"*
(https://github.com/HanaokaYuzu/Gemini-API, accessed 2026-08-17). It therefore depends on a permanently
running Chrome fleet, a cookie harvester, and Google not changing an unversioned internal endpoint.

**The ToS position is the problem, and it is worse than "grey".**

> "Directly accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using
> third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a
> violation of applicable terms and policies."
>
> — *Gemini CLI: License, Terms of Service, and Privacy Notices*,
> https://geminicli.com/docs/resources/tos-privacy/, **Last updated 2026-04-10**, accessed 2026-08-17

And the Gemini API Additional Terms:

> "You also may not attempt to reverse engineer, extract or replicate any component of the Services,
> including the underlying data or models (e.g., parameter weights)."
>
> — https://ai.google.dev/gemini-api/terms, **Effective 2026-03-23, last updated 2026-04-28**,
> accessed 2026-08-17

This is **enforced, not theoretical**. Google's own developer forum carries a steady stream of account
disablings under this clause — e.g. *"Appeal: Gemini API / CLI Access Disabled – 403 ToS Violation"*
(https://discuss.ai.google.dev/t/appeal-gemini-api-cli-access-disabled-403-tos-violation/138337) and
*"[Help Needed] Gemini API Access Disabled - Unintentional ToS Violation (Case: 7-2011000040892)"*
(https://discuss.ai.google.dev/t/help-needed-gemini-api-access-disabled-unintentional-tos-violation-gemini-api-access-disabled-unintentional-tos-violation-need-help-case-7-2011000040892/123477), both accessed
2026-08-17. *Contradiction noted honestly:* these are user reports, not Google statements, so I trust them
as evidence that enforcement **happens** and not as a measurable probability.

**Verdict: do not extend this to Konrad's personal account.** The pool survives precisely because it burns
disposable accounts, not his. Attaching his Ultra identity to a reverse-engineered client puts the
subscription he pays for — and the Google account that holds his Gmail, Drive and Calendar — in the blast
radius of a ToS ban. That trade is not close.

## 5. Route 4 — Antigravity CLI (`agy`) ← **the zero-key route**

### 5.1 The thing the 2026-08-05 research could not have known

Google migrated the subscription entitlements off Gemini CLI:

> "On June 18, 2026, Gemini CLI and Gemini Code Assist IDE extensions will stop serving requests for Google
> AI Pro and Ultra, as well as those using it free of charge."
>
> — *An important update: Transitioning Gemini CLI to Antigravity CLI*, Google Developers Blog,
> **published 2026-05-19**, https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/,
> accessed 2026-08-17

Gemini CLI keeps only paid keys: *"Gemini CLI will remain accessible via paid Gemini and Gemini Enterprise
Agent Platform API keys."* The discontinued tiers *"are now supported via Antigravity CLI"*
(https://github.com/google-gemini/gemini-cli/discussions/27274, dated 2026-05-19, accessed 2026-08-17).

**Version-drift flag:** the Gemini CLI quota page (https://geminicli.com/docs/resources/quota-and-pricing/)
still advertises OAuth tiers of 1,000/day free, 1,500/day Pro, **2,000/day Ultra**. Its "Last updated" is
**Jun 18, 2026 — the very day those tiers were cut off.** Treat those numbers as **stale for Pro/Ultra**.
I record them only so a planner who finds that page recognises it and discards it.

Konrad's plan maps cleanly onto the new tiering. Google restructured on 2026-05-19: Pro at $20/mo (1X
baseline), a new Ultra at $100/mo (5X), and the top Ultra reduced from $250 to **$200/mo at 20X**
(https://antigravity.google/blog/changes-to-antigravity-plans, posted 2026-05-19, accessed 2026-08-17).
**"Ultra 20x" is the top $200 tier** — the multiplier is literally the plan name. That is the entitlement
we would be spending.

Antigravity's own plans page declines to publish hard numbers, and says so:

> "The baseline rate limits are primarily determined to the degree we have capacity."

Ultra gets *"The highest, most generous quota, refreshed every five hours"*, *"Highest weekly rate limits"*
and *"Access to third-party models"*; all plans include *"Access to all product features, such as the
Scheduled Tasks and the CLI"* (https://antigravity.google/docs/plans, accessed 2026-08-17).
**No exact request ceiling is publishable — that is a genuine unknown, not an omission on my part (§9).**

### 5.2 How it actually works on a headless VPS

Docs site confirmed live in a real browser — Antigravity CLI **v1.1.13**, SDK **v0.12**, IDE **v2.5.5**,
Antigravity 2.0 **v2.8.1**, with Linux x64 downloads requiring *"glibc >= 2.28, glibcxx >= 3.4.25"*:

![Antigravity 2.0 docs — Getting Started, version sidebar and Linux requirements](/api/uploads/cb270ce22cab/20260817T041922Z-antigravity-docs.png)
*`/api/uploads/cb270ce22cab/20260817T041922Z-antigravity-docs.png` — browser session, 2026-08-17.*

**Install** (https://antigravity.google/docs/cli/install, accessed 2026-08-17):

```bash
curl -fsSL https://antigravity.google/cli/install.sh | bash   # → $HOME/.local/bin/agy
```

**Login over SSH — this is the crux, and it is designed for exactly our situation:**

> "When running over SSH, the CLI detects the remote connection environment. Because it cannot launch a
> local web browser, the CLI initiates a manual URL loop"

— user receives an authorization URL, opens it in a browser anywhere, returns an alphanumeric code. This is
the same "human logs in once, by hand" shape the AI OS already uses for `research-browser` profiles.
**Konrad does this once. No credential is ever stored by us.**

**Credential storage:** the CLI *"attempts to access your operating system's native secure keyring (such as
Apple Keychain, Linux Secret Service/dbus, or Windows Credential Manager)"*. Per §1.2 this host **serves and
can activate `org.freedesktop.secrets`** — so we land on the supported path.

Official headless guidance (https://antigravity.google/docs/cli/troubleshooting, accessed 2026-08-17):

> "If you are running in a headless environment or over SSH, ensure that a D-Bus session is active and that
> your keyring daemon is running."

> "Ensure your system keyring (such as GNOME Keyring or KWallet) is unlocked and accessible."

with `export $(dbus-launch)` given as the initialisation command.

**Headless invocation** (https://antigravity.google/docs/cli/headless, accessed 2026-08-17):

> "Run Antigravity CLI non-interactively to script agent tasks, integrate with CI pipelines, and capture
> machine-readable output."

```bash
agy -p "Your prompt here" --output-format json
result=$(agy -p "Name three systems..." --output-format json)
```

Flags: `-p` / `--print` / `--prompt`; `--output-format` (`text` | `json` | `stream-json`); `--model`;
`--effort` (low/medium/high); `--agent`; `--dangerously-skip-permissions`; `--print-timeout` (default 5m).
Exit 0 on success, non-zero with detail on stderr. And critically:

> "Headless mode uses your cached credentials. Authenticate once with an interactive `agy` session first."

**Known fragilities — stated plainly:**

1. **Open upstream bug, but not ours.** *"File-based token storage is write-only: fresh process rejects a
   valid antigravity-oauth-token in headless Linux containers"* — issue #479
   (https://github.com/google-antigravity/antigravity-cli/issues/479, filed 2026-06-23, **open**, assigned
   `manirajc`, versions 1.0.8/1.0.10). Fresh processes fail with *"You are not logged into Antigravity."*
   **But the reported environment is "Debian 12, Docker container, non-root user (uid 1001, no D-Bus/keyring
   daemon)"** — the file fallback, taken *because* no Secret Service exists. §1.2 measured that this host
   **does** serve `org.freedesktop.secrets`, so we take the keyring path and never enter the broken branch.
   A builder must still confirm this empirically after login; it is the single highest-risk assumption here.
2. **Keyring must be *unlocked*, not merely installed.** gnome-keyring's default keyring is
   password-protected; headless hosts normally create it with an empty password to auto-unlock. Unverified
   (§9) — it cannot be tested before a login exists.
3. **Silent self-updates.** The installer states `agy` self-updates in the background. A production
   dependency that rewrites its own binary can change flags or auth behaviour without a deploy. Pin/monitor.
4. **Closed source.** Antigravity CLI is closed-source, unlike Gemini CLI — reported by The New Stack
   (https://thenewstack.io/google-antigravity-cli/, accessed 2026-08-17). Secondary source, flagged as such.

### 5.3 The Antigravity SDK is *not* the zero-key route

Tempting — `pip install google-antigravity`, a Python agent framework — but it authenticates the wrong way.
The official overview page (https://antigravity.google/docs/sdk/overview, accessed 2026-08-17) **does not
document authentication at all**; the auth description I found comes from a secondary source stating the SDK
*"uses Application Default Credentials (ADC)"* and, for Gemini Enterprise Agent Platform (formerly Vertex
AI), `LocalAgentConfig(vertex=True)` with a GCP project and location
(https://www.aimadetools.com/blog/antigravity-sdk-custom-agents-guide/, accessed 2026-08-17).

**ADC means GCP means billing — i.e. Route 1 wearing a nicer jacket.** I mark this **medium confidence**:
the claim rests on a secondary source because the primary page is silent, and I could not verify it by
running the SDK (that would be implementation). A builder should confirm before relying on it. It does not
change the recommendation either way — nothing suggests the SDK rides a consumer Ultra subscription.

## 6. Comparison

| Route | Setup cost | Fragility | ToS risk | Uses the token we already hold? | Uses Ultra 20x? |
|---|---|---|---|---|---|
| **Antigravity CLI `agy`** ⭐ | Install script + **one** SSH paste-a-code login by Konrad | **Medium** — keyring must stay unlocked; binary self-updates; issue #479 lurks if keyring ever goes away | **None** — first-party client, headless mode officially sanctioned | No — its own OAuth, stored in the OS keyring | **Yes** |

| Reuse our Google OAuth token directly | — | — | — | **No: proven 403, §1.1** | No |

### 6.1 The constraint that most shapes the build

Whatever is built, it must **execute the `agy` binary** and read its stdout. It must **not** read
`~/.gemini/antigravity-cli/antigravity-oauth-token`, or the keyring entry, and call
`cloudcode-pa.googleapis.com` itself — even though §1.2 shows that endpoint is reachable and it would be
technically easy. The ToS clause in §4 names this exact pattern ("using OpenClaw with Gemini CLI OAuth") as
a violation. **Shelling out is compliant; token-lifting is a ban risk on Konrad's primary Google account.**
Put this in the builder's brief in these words, because the shortcut is genuinely tempting.

## 7. RECOMMENDATION

**Primary: Antigravity CLI (`agy`), shelled out, authenticated once by Konrad over SSH.**

Because it is the only route that satisfies all three of Konrad's constraints simultaneously — no API key,
no new billing, and it actually spends the Ultra 20x subscription he already pays for — while carrying
**zero ToS risk**, which the cookie pool cannot claim and which matters enormously when the account in
question also holds his Gmail, Drive and Calendar. This host is measurably in the supported configuration
(§1.2), and the login shape is one Konrad already performs for browser profiles.

**Fallback, offered in the same panel: AI Studio API key.** One paste, effectively zero fragility, works
instantly, and honestly beats the recommended route on robustness. Konrad should be able to choose it
without a conversation — a fragile zero-auth flow is not automatically better than a one-paste flow, and if
`agy` auth proves flaky in practice, this is the escape hatch.

**Explicitly not recommended: extending the cookie pool to his personal account** (§4), and **not the SDK**
(§5.3).

**Leave the existing pool exactly as it is.** It works, it is isolated on disposable accounts, and
`gemini-qa.mjs` depends on it. This work should *add* a route, not migrate one.

## 8. What the settings panel should render

For the recommended route, the panel's job is to **walk Konrad through a one-time human login and then show
truthfully whether it still works.** Two providers, one card each.

**Card A — "Gemini via Antigravity (Ultra subscription)"** — recommended, no key.

States to render:

1. **Not installed** — "Antigravity CLI is not installed on this server." Primary button *Install*, which
   runs the bootstrapper and streams its output. Show the resolved binary path (`~/.local/bin/agy`) and
   version on success.
2. **Installed, not authenticated** — the important screen. Konrad must run the interactive login himself;
   the panel cannot do it for him. Render:
   - the exact command to run over SSH, copyable: `agy` (first interactive run triggers the URL loop);
   - the explanation that `agy` will print an authorization URL, he opens it in any browser, signs in with
     **the Google account carrying the Ultra 20x subscription**, and pastes the returned code back;
   - a *"I've logged in — re-check"* button that re-probes.
3. **Authenticated / healthy** — show the account email if `agy` exposes it, the plan tier if available,
   the CLI version, and *last successful call* timestamp. A *Test* button that runs
   `agy -p "reply with OK" --output-format json` and renders the round-trip time and raw result.
4. **Broken** — distinguish the failure modes, because they need different human actions:
   - `"You are not logged into Antigravity"` → re-auth needed (the §5.2 keyring failure). Say *"the server's
     keyring is locked or unavailable"* and link the troubleshooting note, don't just say "error".
   - non-zero exit with quota language → *"Ultra quota exhausted; refreshes every five hours"* (§5.1).
   - binary missing after a self-update → back to state 1.

Do **not** render a quota gauge with invented numbers. Google does not publish Ultra's ceiling (§5.1) and
the panel must not imply a precision that does not exist — show consumption if `agy` reports it, otherwise
show nothing.

**Card B — "Gemini via API key"** — fallback, one paste.

A single secret input writing to `/opt/ai-os/.secrets/store/gemini-api-key` (the path
`scripts/gemini-qa.mjs` already reads), with a deep link to `https://aistudio.google.com/apikey` labelled so
he knows he will hit a Google sign-in (§3), and a *Test* button. Show the free-tier reality plainly —
*"a key on a project without billing is Flash-only, ~250 requests/day"* — so the choice is informed.

**Cross-cutting:** one radio/segmented control for which provider the OS actually uses, since
`gemini-qa.mjs` requires an explicit backend and forbids automatic fallback by design. Never silently fail
over — that script's header documents exactly why. Design tokens only, both themes, per the project brief.

## 9. What I could NOT verify, and why

1. **Ultra 20x's exact request ceiling on Antigravity.** Google deliberately does not publish it — *"The
   baseline rate limits are primarily determined to the degree we have capacity."* Not knowable from
   documentation; only measurable after login.
2. **That `agy` login actually persists on this host.** Everything upstream of it checks out (§1.2), but the
   proof requires completing an OAuth login as Konrad — which the brief forbids and I did not attempt. This
   is the single assumption that could sink the recommendation; a builder must test it immediately after
