**Summary:**
| Column | Type | NULLable | Reliably Populated for Completed Project-Task Run |
|--------|------|----------|--------------------------------------------------|
| `created_at` | timestamptz | NO | YES — set at INSERT (line 100, db/runs.ts) |
| `updated_at` | timestamptz | NO | YES — refreshed on every state change (executor.ts line 157) |

| `last_heartbeat_at` | timestamptz | YES | YES if run entered 'running' state (executor.ts line 154: set on every claim heartbeat) |

**For a completed project-task run, the guaranteed-reliable timestamps are:**
- `created_at` (task queued)
- `updated_at` (task last touched, always refreshed before completion)
- `started_at` (task first claimed from queue, only NULLable if never claimed)
- `completed_at` (task entered terminal state, only NULLable if still running; for a completed run, always set)

## 3. Spend and usage per run

**Spend (`runs.spent_usd`):**  
Column in the `runs` table, `numeric(10,2)` — set at INSERT (defaults to 0, line 95 of migration 0021), incremented by executor.ts line 153 during run execution:
```typescript
UPDATE runs SET spent_usd = COALESCE(spent_usd, 0) + $2, updated_at = now()
```

**Usage tokens (`runs.metadata.usage_total_running`):**  
Written by **lib/run-rollup.ts** (line 325, in `buildPayload()`):
```typescript
usage_total_running: s.usageTotal,  // CcTokenUsage aggregate
```

Where `CcTokenUsage` (line 41–46, run-rollup.ts):
```typescript
const EMPTY_USAGE: CcTokenUsage = {
  input_tokens: 0,
  output_tokens: 0,
  cache_read_input_tokens: 0,
  cache_creation_input_tokens: 0,
};
```

The aggregate `s.usageTotal` is incremented every time an `assistant_text` event with usage arrives (line 264, run-rollup.ts: `sumUsage(s.usageTotal, usage)`).

**Worked example from db/projects.ts `listManagerRollup()` (lines 358–398):**
```sql
WITH worker_agg AS (
  SELECT
    (metadata->>'project_id')::uuid AS project_id,
    SUM(COALESCE((metadata->'usage_total_running'->>'input_tokens')::bigint, 0))  AS tokens_in,
    SUM(COALESCE((metadata->'usage_total_running'->>'output_tokens')::bigint, 0)) AS tokens_out,
    SUM(COALESCE(spent_usd, 0)) AS spent_usd,
    MAX(updated_at) AS last_activity_at
  FROM runs
  WHERE metadata ? 'project_id'
    AND parent_run_id IS NULL
  GROUP BY (metadata->>'project_id')::uuid
)
```

**Summary:**
- **`runs.spent_usd`** — direct column, numeric, always populated for any run that incurred cost
- **`runs.metadata.usage_total_running.input_tokens`** — bigint, cumulative input tokens from all assistant messages
- **`runs.metadata.usage_total_running.output_tokens`** — bigint, cumulative output tokens from all assistant messages
- Only **top-level runs** (`parent_run_id IS NULL`) are summed to avoid double-counting sub-agent runs

## 4. Proxy for "when did a project task actually start running"

**Problem:** `project_tasks` table has only `created_at` and `updated_at`, no `started_at`.

**Best available proxy:**  
```sql
SELECT r.started_at
  FROM project_tasks pt
  JOIN runs r ON r.id = pt.run_id
  WHERE pt.id = $1
```

**Why this is the proxy:**
1. When a run is claimed from the queue in `executor.ts:claimNextRun()` (line 153), `started_at` is set:
   ```sql
   started_at = COALESCE(r.started_at, now()),
   ```
   This is the only place `started_at` is populated (on first claim).

2. For a project task, `started_at` represents when the executor FIRST claimed the run from the queue and began executing it — the wall-clock boundary between "queued" and "running".

**Error margin:**
- **If the run never entered 'running' state (still queued or failed while queued):** `started_at` is NULL. This is correct — the task never started.
- **If the run was parked behind `wake_after` (usage wall recovery):** The executor will NOT claim it until `wake_after <= now()`, so `started_at` is delayed by the wake interval. The delay is honest — the task genuinely was not runnable during that window.
- **Skew:** The claim query uses `now()` at execution time, so `started_at` is set to the server's wall clock when the executor polls. Skew vs. the client's clock is inherent to any server-side timestamp.

**No better alternative exists:**
- `project_tasks.created_at` is when the task was created (usually round before), not when it started.
- `project_tasks.updated_at` is refreshed every time the task's status changes, but is not granular enough (updated when status becomes 'running', but the status-transition write and the row update are not atomic with the run's `started_at`).
- `runs.last_heartbeat_at` is refreshed on every poll after the run starts (executor.ts line 154), so it is NOT the "start" time.

## 5. Existing scripts for duration/concurrency measurement

**Search:** grep across `scripts/` and `forge-control/scripts/` for patterns matching duration, concurrency, elapsed, wall-clock measurement.

**Result:** No existing script found that computes project run durations or concurrency across a project.

**Closest artifact:** `scripts/checks/check-story-digest.ts` computes `elapsed_ms` for individual runs (elapsed from `started_at` to `completed_at`, with fallback handling for running runs). This is run-level only, not project-aggregate. Does not touch project_tasks.

**Implication:** Phase 7's measurement instrument is a net-new script. It will need to:
1. Query `project_tasks` joined with `runs` via `run_id`
2. For each run in a project, compute elapsed = `completed_at - started_at`
3. For each round, track task concurrency (how many runs overlap in time during a round)
4. Distinguish actual parallel runs (different worktreams in Fix B) from serialized runs (same round today)

## 6. What makes a naive concurrency measurement WRONG

**At least three blind spots:**

### a. Sub-agent runs (parent_run_id IS NOT NULL) double-count
When an agent spawns a sub-agent via the Task or Agent tool, a new `runs` row is created with the parent's `parent_run_id` set. A naive count of all runs in a time window will count the parent and every child, inflating concurrency.

**Fix:** Only count top-level runs: `parent_run_id IS NULL`.  
**Evidence:** `listManagerRollup()` at db/projects.ts line 369 explicitly filters: `AND parent_run_id IS NULL`.

### b. Runs parked behind wake_after count as active
When the executor re-queues a run after a usage wall hit (e.g., quota exhaustion), it sets `wake_after` to a future timestamp (db/runs.ts line 562, `requeueRunAfterUsageWall()`). The run is `status = 'queued'` but hidden from the claim query until `wake_after` passes.

A measurement that counts all runs with `status IN ('queued','running')` without checking `wake_after` will count parked runs as active, inflating concurrency and duration.

**Fix:** Filter to runs actually claimable: `(wake_after IS NULL OR wake_after <= now())`.  
**Evidence:** `claimNextRun()` at executor.ts line 146: `AND (wake_after IS NULL OR wake_after <= now())`.

### c. 'stuck' runs never end, falsely extending wall-clock duration
A run can transition to `status = 'stuck'` if `last_heartbeat_at` does not update within a timeout window. A stuck run carries neither `completed_at` (it is not finished) nor a clear end time.

A naive duration computation using `completed_at - started_at` will either ignore stuck runs entirely (undercount) or use `updated_at` as a proxy (overcount, because `updated_at` is refreshed on every status poll).

**Fix:** Decide what "duration" means for a stuck run:
- Is it the wall-clock time to detection (now - started_at, including the stuck wait)?
- Is it the last known progress (last_heartbeat_at - started_at)?
- Is it unknown, and the run should be marked as "incomplete measurement"?

**Evidence:** Stuck runs are identified by executor watchdog (executor.ts line 857+), which reads `last_heartbeat_at` and sets status = 'stuck' if it has gone stale. No explicit end time is recorded for a stuck run.

### d. Archived runs (archived = true) are not necessarily complete
In migration 0031, `archived` was added to soft-delete chats. Archiving also cancels non-terminal runs (line 457, db/runs.ts):
```sql
status = CASE WHEN status = ANY($2::text[]) THEN 'cancelled' ELSE status END,
```

A run can be archived + cancelled, or archived + completed. A naive filter (`archived = false`) will exclude measurement data for deliberately closed work, leading to a false picture of what was actually attempted.

**Fix:** Clarify whether the measurement should include archived runs. If measuring "what we attempted", include them. If measuring "what the fleet is currently doing", exclude them. **Declare the choice in the measurement report.**

## Edge cases the instrument must state explicitly

1. **Parent vs. child runs in token cost:** Both parent and child appear in the runs table; only the parent's `spent_usd` and `usage_total_running` are meaningful for project-level accounting. Sub-agent runs (parent_run_id IS NOT NULL) should be VISIBLE for debugging but EXCLUDED from the sum.

2. **Incomplete started_at for queued tasks:** A task stuck in 'pending' or 'ready' will have no run yet (run_id IS NULL). A task queued but not yet claimed has a run with `started_at IS NULL`. The instrument must distinguish these states.

3. **Round-level concurrency is a derived graph, not a number:** Today a "round" is a barrier — all tasks in round N must be done before any in round N+1 starts. In that model, concurrency per round is: max(concurrent tasks in round N across all time). Once the DAG (Fix A) lands, a "round" becomes derived (longest-path depth from roots), and concurrency becomes "tasks with overlapping [created_at, completed_at] windows". The instrument's output must state which model it is measuring.

1. ✅ Read timestamp columns from runs (all reliable for completed runs)
