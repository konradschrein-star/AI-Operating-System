Real project runs show consistent metadata structures, large thread payloads (200–438 entries), and rich subagent taxonomies. The data needed for U22–U24 (orientation strip, readable transcript, story-so-far digest) already exists in the database without new plumbing. ## Current Activity Taxonomy

Real `metadata.current_activity` entries observed:

| Kind | Tool | Text Presence | Real-World Meaning |
|------|------|---------------|-------------------|
| `assistant_text` | null | Long (50–200B) | Agent's prose; prose-heavy stages |
| `tool_call` | "Bash"\|"Read"\|"Edit"\|"Write"\|"Grep" | null or tool name | Agent is interacting with a tool |
| `tool_result` | (from meta.tool) | Outcome snippet | Tool returned a result; agent processing |
| `thinking` | null | null | Extended thinking in progress |

**Derivation note:** The `current_activity` is stamped by the executor on every thread event, frozen at settlement. It is the LAST event chronologically, so for display:
- A settled builder showing `tool_call: Bash` at `08:57:27` means it ended mid-bash-thinking.
- A settled builder showing `assistant_text` at `08:58:13` means it ended writing prose (typically a summary).

## Subagent Metadata Structure

Every subagent in `metadata.subagents_v2` carries:

```typescript
{
  tool_use_id: string;           // Stable spawn identity
  role: string;                  // "architect"|"builder"|"reviewer"|"scout"|...
  model: string | null;          // "claude-haiku-4-5-20251001", null if not yet resolved
  started_at: string;            // ISO timestamp of Agent() call
  ended_at: string | null;       // ISO timestamp of tool_result; null while running
  updated_at: string;            // Last event in the subagent's thread
  description: string | null;    // The spawn's human-readable brief
  status: "running" | "done";    // Derived: ended_at ? "done" : "running"
  usage: Usage;                  // { input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens }
  event_count: number;           // Count of thread entries tagged with this parent_tool_use_id
  latest_activity: {             // Last event of this subagent
    kind: string;
    tool: string | null;
    text: string | null;         // Clipped to 160B
    ts: string;
  } | null;
}
```

## Thread Payload Characteristics

### Entry Sizes
Real entries sampled from runs 298–438 entries long:

- **User instructions (first entry):** ~2–3KB (large upfront system prompt + task)
- **Assistant prose blocks:** 200B–1.5KB per block
- **Tool call + result pairs:** 300B–2KB per pair (Bash, Read, Grep, Edit, Write)
- **Subagent spawns (Agent tool_call):** 1–3KB (includes full spawn input)
- **Heartbeat/status updates:** 50–200B

**Total thread size range:**  
- Small (100 entries): ~50–150KB
- Medium (200 entries): ~150–400KB  
- Large (400 entries): ~400KB–1.2MB

### Tool Call Taxonomy (from thread meta)

Real tool calls in thread entries use `meta.tool`:

| Tool | Meta Keys Present | Sample Size |
|------|-------------------|-------------|
| Bash | `tool`, `tool_use_id`, (input: bash command) | 1–2KB |
| Read | `tool`, `tool_use_id`, (input: file path) | 500B |
| Write | `tool`, `tool_use_id`, `input` (content snippet) | 1–3KB |
| Edit | `tool`, `tool_use_id`, `input` (old_string, new_string, file) | 1–2KB |
| Grep | `tool`, `tool_use_id`, `input` (pattern, files) | 500B–1KB |
| Task/Agent | `tool`, `tool_use_id`, `spawns_subagent_role`, `input` (full JSON) | 2–4KB |
| Skill | `tool`, `tool_use_id`, `input` (skill name, args) | 500B–1KB |

## Recommended One-Line Summaries per Tool

### U23 Implementation: ToolCallRow Rendering

For collapsed transcript rows, render tool calls as:

```
🔧 [Tool Name] [Argument Gist] → [Outcome Summary]
```

**Format by tool:**

| Tool | Collapsed Format | Expandable To |
|------|------------------|--------------|
| **Bash** | `🔧 bash ‹cmd gist› → ‹exit code + first error line or ✓›` | Full command, full stdout/stderr |
| **Read** | `🔧 read ‹file path› → ‹size + first line or ✗›` | Full file path, file content (async-loaded) |
| **Write** | `🔧 write ‹file path› → ‹size bytes written›` | Full file path, content written |
| **Edit** | `🔧 edit ‹file:line› ‹old (N bytes)› → ‹new (N bytes)›` | File, full old/new strings, line numbers |
| **Grep** | `🔧 grep ‹pattern› [glob] → ‹N matches›` | Full pattern, files, all matches |
| **Task/Agent** | `🔧 spawn ‹role› ‹description› → ‹status: running/done›` | Full spawn input, subagent status, subagent thread (drilled) |
| **Skill** | `🔧 skill ‹name› → ‹result preview›` | Full skill name, args, full result |

**Implementation data source:**  
- Tool name and arguments: `thread[i].meta.tool`, `thread[i].meta.input`
- Outcome: `thread[i+1]` if `kind === 'tool_result'` and `meta.tool_use_id` matches, or `thread[i].content` for tool_result entries
- First-error lines: Bash results often contain `stderr`, grep by regex to extract the first non-empty line

## Derivation-Only Story-So-Far Digest (U24)

### What the Digest Can Honestly Contain (No New LLM)

For sessions with >50 thread entries, render a collapsed digest at the top:

```markdown
**Session Brief**
- Task: [from first user entry, extract the bolded task name]
- Started: [started_at]
- Elapsed: [settled_at - started_at for settled, or clock for running]
- Status: [running/completed/failed]

**Progress**
- Events: [thread count] entries, [N tool calls], [N errors or 0]
- Subagents: [count + list of roles, or "none"]
- Model: [model_resolved], effort: [effort], engine: [engine]

**Key Turns** (last 3 assistant prose blocks, max 100B each)
1. [Prose block, ts]
2. [Prose block, ts]
3. [Prose block, ts]

**Outcome** [last entry's content, max 200B]
```

### Derivation Algorithm (Read-Only)

```typescript
function deriveDigest(run: AgentRun, thread: ThreadEntry[]): Digest {
  // Task: extract from first user entry's title or content
  const firstUser = thread.find(e => e.role === 'user' && e.kind !== 'tool_result');
  const task = extractBoldedPhrase(firstUser?.content) || run.title;

  // Progress counts
  const toolCalls = thread.filter(e => e.kind === 'tool_call').length;
  const errors = thread.filter(e => e.kind === 'error' || e.content?.includes('error')).length;
  
  // Subagents: from metadata.subagents_v2 or folded from thread
  const subagents = run.subagents || foldSubagents(thread);
  const subagentRoles = [...new Set(subagents.map(s => s.role))];

  // Key turns: last 3 assistant prose blocks (non-tool-related)
  const proseTurns = thread
    .filter(e => e.role === 'assistant' && !e.meta?.tool && e.kind !== 'tool_result')
    .slice(-3)
    .map(e => ({ text: e.content.slice(0, 100), ts: e.ts }));

  // Outcome: last entry
  const lastEntry = thread[thread.length - 1];

  return {
    task,
    started_at: run.started_at,
    elapsed_ms: run.elapsed_ms,
    status: run.status,
    event_count: thread.length,
    tool_calls: toolCalls,
    errors,
    subagents: subagentRoles,
    key_turns: proseTurns,
    outcome: lastEntry?.content?.slice(0, 200),
  };
}
```

### What the Digest CANNOT Honestly Derive

- **Causality**: Which tool call led to which error. (The thread has order but not explicit causality; an error may lag the tool call by several entries.)
- **Branching**: If a builder tried approach A, abandoned it, then tried B. (The digest sees the order but not the intent to abandon.)
- **Quality assessment**: Whether the work is "good" or "sound". (That is a judgment call for the agent or reviewer, not derivable from raw entries.)
- **External context**: Why a task took so long or what it was blocking. (Only the agent/user knew the intent.)

**If the builder's work requires a narrative that the digest cannot derive, the builder should add a summary block to their final assistant message** (e.g., "# Summary: Fixed A by doing X, then fixed B by doing Y when A's approach broke"). The digest picks that up as the last prose block.

## Orientation Strip Data (U22)

For the drill-in view at the top, all fields derive from existing data:

```typescript
interface OrientationStrip {
  role: string;                    // From run.metadata.role
  model: string | null;            // From run.model_resolved
  task_title: string | null;       // From project_tasks.title (if linked) or run.title
  round: number | null;            // From project_tasks.round (if linked)
  phase: string | null;            // From plan's phase name (if linked)
  current_activity: string;        // From run.metadata.current_activity, human-readable
  phase_position: string;          // "Phase 500 of 15-ui-v3-phases.md; next: 600"
}
```

**Data source:**
- `role`, `model`: run.metadata
- `current_activity`: formatted from `run.metadata.current_activity` with the taxonomy above
- `task_title`, `round`, `phase`: join via `run.metadata.project_id` → `project_tasks` → plan docs (if present)
